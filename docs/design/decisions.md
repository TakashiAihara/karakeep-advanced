# 設計上の決定記録

`extensions/tab-group` の roadmap を組むにあたって決めたことと、その理由。
決定は上から時系列。覆すときは行を書き換えず、新しい決定を下に足して「D0N を覆す」と書く。

判断の材料になった調査は `docs/design/roadmap.md` と、各 issue の「背景」節にある。

## D01 — restore したグループは既定で残し、消すかどうかを選べるようにする

決定日: 2026-08-28 / 状態: 採用

OneTab は「復元 = そのグループを消費する」が既定で、復元したタブはリストから消える。
現実装の `openGroup` は読むだけで list を消さないため、使い続けると sub-list が単調増加する。

検討した案:

- (a) OneTab 準拠で Open all したら削除する
- (b) 現状維持で常に残す
- (c) options で既定を決め、行ごとに「開くだけ / 開いて消す」を出す

**(c) を採用。**

Karakeep をバックエンドに置いた動機は「機種変やプロファイル破損でタブが消えるのを止める」ことで、
これはアーカイブとしての要求。一方 OneTab の日常運用は「ウィンドウを一旦退避して、後で消費する」で、
こちらは一時退避としての要求。**この 2 つは別物で、どちらも実際に要る。**
(a) はアーカイブ用途を壊し、(b) は一時退避用途で片付けが進まない。

既定は「残す」にする。破壊的でない側を既定にし、消す操作は明示的に選ばせる。

## D02 — ツールバーアイコンは popup のままとし、ドキュメント側を直す

決定日: 2026-08-28 / 状態: 採用

`docs/karakeep-advanced.md` の Phase 1 表は
「ツールバーアイコン 1 クリックで全タブ保存 + 全タブ閉じる (OneTab デフォルト挙動を踏襲)」と書いているが、
実装はアイコンクリックで popup が開き、Save を押す 2 アクションになっている。

**実装を正とし、ドキュメントを直す。**

理由は 2 つ。

- 即保存はショートカット (`Ctrl+Shift+E` = `save-tab-group`) が既に担っており、動線として失われていない
- アイコンから popup が開かないと、Recent / Search / Import に到達する手段が消える。
  ツールバーアイコンは拡張の唯一の常設 UI で、そこを 1 アクションの副作用に割り当てると閲覧系が孤立する

OneTab の既定挙動を再現したい場合は、ショートカットのキー割り当てを変えれば済む。

## D03 — マネージャーページ (M3) を作る

決定日: 2026-08-28 / 状態: 採用

popup は 360px 幅で、Recent は 20 件固定。
OneTab の中核操作「グループの中身を見て、要るものだけ取り出して残りは捨てる」を置く場所が無い。

さらに `GET /lists` にはページングもフィルタもソートも無い (`schema.d.ts:229` が `query?: never`) ため、
一覧の絞り込みは必ずクライアント側で行うことになる。その状態を持つ場所としても専用ページが要る。

**`entrypoints/manager/` を新設する。** ただし着手順は M0 → M1 → M2 の後。
土台 (保存の信頼性・サーバー側メタデータ) が無い状態で閲覧 UI を作ると、
表示するデータそのものが信用できない。

popup は「素早く保存する入り口」として残し、閲覧・整理・大量操作をマネージャーページに寄せる。

## D04 — 共有 URL 生成はやらない

決定日: 2026-08-28 / 状態: 採用 (スコープ外に確定)

`docs/karakeep-advanced.md` の Phase 3 に「共有 URL 生成 (Karakeep の public 機能で代替できるか要検証)」がある。
調査した結果:

- `List` に `public: boolean` が実在し (`schema.d.ts:887`)、`PATCH /lists/{listId}` の body でも設定できる (`:1937`)
- **共有 URL を発行・取得する endpoint は 33 パス中に存在しない**

つまりフラグは立てられるが、URL は API の外にある。

**やらない。** 拡張側で Karakeep 本体の URL 規則を組み立てると、
本体のルーティング変更で黙って壊れる。しかも壊れ方が「共有 URL が間違っている」形になり、
共有した相手が 404 を踏むまで気づけない。フラグを立てるだけの機能は本体 UI でできることの劣化コピーなので作らない。

Karakeep 本体が共有 URL を返す API を生やしたら再検討する。

## D06 — グループのメタデータは `List.description` に「人向け 1 行 + JSON 1 行」で持つ

決定日: 2026-08-28 / 状態: 採用

現状はタブ件数をグループ名の正規表現 (`/\((\d+)\s*tabs?\)\s*$/`) から復元しているため、
Phase 2 で入れた rename 機能を使った瞬間に件数が失われる。

`List.description` がサーバー側に実在し、`GET /lists` で返り `PATCH` で書ける (`schema.d.ts:878` / `:1933`)。

検討した案:

- (a) 1 行 JSON のみ
- (b) 人が読める 1 行のみ + 正規表現でパース
- (c) 人向け 1 行 + JSON 1 行の 2 行

**(c) を採用。**

`description` は Karakeep 本体 UI にもそのまま表示されるので、(a) は本体側に生 JSON が並ぶ。
(b) は結局パースが正規表現に戻り、今と同じ壊れ方をする。

形式:

```
12 tabs · saved 2026-08-28 15:00
<!-- ka:{"v":1,"tabCount":12,"savedAt":"2026-08-28T06:00:00Z","lastOpenedAt":null} -->
```

- パースは `<!-- ka:` で始まる行の JSON だけを見る。人向け行は一切パースしない
- JSON 行が無い / 壊れている場合は `tabCount: null` にフォールバックし、例外を投げない
- 既存グループには JSON 行が無いので、この経路が実際に通る

**chrome.storage に持つ案は採らない。** `chrome.storage.local` は端末間で同期されないため、
別マシンで開いた瞬間にメタデータが空になる。これは Karakeep をバックエンドに選んだ理由と正面から矛盾する。
chrome.storage は引き続き「MRU 表示順のキャッシュ」に限定し、権威データとしては使わない。

`lastOpenedAt` を持たせるのは M4 (auto-archive) の前提。
List に archived フラグは無いので、アーカイブは `parentId` の PATCH で別の親 list に移す方式になる (`schema.d.ts:1935`)。
